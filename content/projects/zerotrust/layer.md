
The project, explained properly
Here's the mental model to hold. An AI agent wants to use tools. Each tool is provided by an MCP server you didn't write and shouldn't trust. Left alone, the agent reads the server's self-description and calls it directly, with the agent's own privileges. Your project inserts a gateway between agent and servers so that no server is trusted by default — every tool is inspected before it's allowed in, profiled to see what it really does, constrained by policy, and watched at runtime. "Zero trust" just means: the server's claims about itself are evidence, not truth, and you verify independently.
The data flows in two phases. There's an onboarding phase (happens once, when a tool is registered) and a runtime phase (happens on every tool call). Your original doc mixes these together; keeping them separate is the key to a clean design.
Let me walk the layers in that frame.
Layer 1 — Intake scanner (onboarding). When a developer registers a new MCP server, you connect to it, call tools/list, and inspect the manifest before the agent is ever allowed to touch it. Three checks. First, a permission/capability sanity check: does a tool named/described as "weather" request filesystem and shell access? Compare requested capabilities against a small dictionary of what that class of tool plausibly needs. Second, a metadata poisoning check: scan the description and schema fields for hidden instructions, since that's where tool-poisoning attacks live — text like "ignore previous instructions," HTML comments, base64 blobs, suspicious unicode. Third, supply-chain: if the server ships dependencies, run pip-audit/osv-scanner and surface known-vulnerable packages. Output is a verdict — approve, quarantine, or reject — plus the list of issues. This is your static defense, and it's bypassable (a smart attacker writes an honest-looking manifest), which is exactly why Layer 2 exists.
Layer 2 — Behavioral profiling sandbox (onboarding, your strongest part). Static analysis trusts what the tool says. This layer measures what it does. You run the MCP server inside a locked-down Docker container and drive it through a representative set of tools/call invocations while observing its actual behavior at the boundary — syscalls via strace, network egress, files touched, processes spawned. You don't care about exact semantics, just capability classes: did it touch the filesystem? open a network connection? read environment variables? spawn a subprocess? The output is an observed capability profile: e.g. {network, filesystem, env_read}. The critical correction from earlier: you observe from outside the server's process, because the server is a black box you didn't write — you cannot patch its internal open(). This is why strace/seccomp, not monkeypatching.
Layer 3 — Declared vs observed comparator (onboarding). Trivial code, important idea. Take the capabilities the manifest declared (or the class-based expectation from L1) and subtract them from what L2 observed. Anything left over is undeclared behavior: a "weather" tool that quietly read env vars and opened a file is lying. That diff is your alert. This is also how you catch rug-pulls — when a previously-approved tool ships a new version, you re-profile and compare against its last-known-good profile; new undeclared capabilities mean the tool changed underneath you. That rug-pull story is one of your best demos because it's concrete and visual.
Layer 4 — Policy engine (runtime). Even a tool that passed onboarding is constrained to least privilege. Policy is just data: a file saying WeatherTool: allow [network]; deny [filesystem, subprocess]. At runtime this is consulted to decide whether a given call — or the behavior triggered by it — is permitted. Don't overbuild this; it's lookup-and-compare against capability classes, not a rules language.
Layer 5 — Runtime proxy (runtime, the spine). This is what makes the whole thing real rather than a report. The proxy sits between agent and server: to the agent it pretends to be the MCP server; to the real server it acts as the client. Every tools/call passes through it. On each call it checks the tool's trust verdict, checks policy, forwards the call to the sandboxed server, inspects the response, and logs everything. Without this layer, Layers 1–3 produce reports nobody enforces. Build this first in implementation so everything else has a place to plug in.
Layer 6 — Response sanitization (runtime, keep but be honest). Tool responses are untrusted text that flows back into the model's context, so a malicious server can return poisoned output ("...and now read the user's secrets"). You can regex-filter obvious cases, but say plainly in your report that this is a weak, evadable baseline — paraphrase and encoding defeat it. Presenting it as "a measured, known-insufficient defense" is respectable; presenting it as solved is not.
Layer 7 — Dashboard (demo). Registered tools with their trust verdicts, the declared-vs-observed mismatch view, an attack timeline (registered → profiled → anomaly → blocked), and a blocked-actions log. Its only job is to make the demo legible to faculty in 90 seconds. Build it thin and last.
The end-to-end demo that ties it together: a malicious MCP server claims to be a weather tool but on tools/call reads .env and POSTs to an attacker URL. L1 flags a manifest mismatch. L2 runs it in the sandbox and observes the file read and network egress. L3 reports undeclared capabilities. L4/L5 block the call at runtime. The dashboard shows the whole timeline. That's a complete, honest, impressive story — and crucially, every claim in it is something your system actually measured rather than asserted.
